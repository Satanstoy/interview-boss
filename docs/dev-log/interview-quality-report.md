**[候选人 T12]** MySQL 默认的 InnoDB 引擎用的是 B+ 树来做索引。

**[候选人 T13]** 主要两大类：**链地址法**和**开放寻址法**。

**链地址法**就是每个桶挂一个链表，冲突的元素都插到同一个链表里。优点是实现简单，负载因子超过 1 也还能正常工作；缺点是链表太长的话退化成 O(n)，而且每个节点都有指针开销，内存不太连续，缓存不友好。Java 的 HashMap 就用的这个，链表长度超过 8 会转成红黑树来避免退化。

**开放寻址法**是冲突了就在表里找下一个空位放进去，探测方式有线性探测、二次探测、双重哈希。优点是数据都存在连续数组里，缓存友好；缺点是负载因子不能太高，一般到 0.7 左右就得扩容，否则探测链越来越长，性能急剧下降。Python 的 dict 底层就是开放寻址，用的是一种叫"扰动函数"的探测策略。

简单总结就是：**链地址法对高负载因子容忍度好，开放寻址对缓存友好但对负载因子敏感**。实际选型看场景，内存紧张、查询密集选开放寻址，插入删除频繁选链地址法。

一个请求的生命周期大致是：

1. **Uvicorn接收请求**，交给Starlette处理
2. **中间件链**，比如CORS、日志、异常捕获这些，按注册顺序执行
3. **路由匹配**，找到对应的path function
4. **参数校验**，这是FastAPI的亮点——自动把query、body、path参数用Pydantic做类型校验和解析
5. **执行路径函数**，这里就分两种情况了：如果是`async def`，直接在事件循环里跑；如果是普通`def`，会被扔到线程池里执行
6. **返回响应**，再反向走一遍中间件链

异步的优势主要体现在**IO密集型场景**。InterviewBoss里最核心的IO就是调LLM API，一次请求可能要等几秒钟。用async的话，等待期间事件循环可以去处理其他用户的请求，吞吐量就上来了。如果是同步阻塞的话，一个用户调LLM的时候，其他用户就得排队。

不过有个细节值得注意：FastAPI里即使用同步的`def`，它也会自动放到线程池执行，不会真的阻塞

**[候选人 T13]** 这个是典型的**事件循环阻塞问题**。

`requests`是同步的，它发起HTTP请求后会**阻塞当前线程直到收到响应**。在`async def`里调的话，因为async函数是直接跑在事件循环里的，没有线程池兜底，所以**整个事件循环会被卡住**。

后果就是：LLM调用这几秒期间，这个进程**一个其他请求都处理不了**。高并发时直接雪崩——前面的请求还没回来，后面全排队等着。

正确的做法有两种：
1. 用`aiohttp`或`httpx`的异步客户端替代`requests`
2. 如果一定要用同步库，用`asyncio.to_thread()`把它包一下，扔到线程池去执行

说实话我开发InterviewBoss初期就踩过这个坑，用的是OpenAI官方的同步SDK，调试的时候单用户没问题，一模拟多个用户并发就发现延迟严重飙升。换成了`httpx`的async client之后才好。
