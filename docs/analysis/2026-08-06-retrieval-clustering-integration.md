# 模拟面试检索 × 题目聚类：实验结论整合分析

**日期**: 2026-08-06
**来源**: 聚类实验（`docs/tdd-reports/2026-08-05-cluster-memory-label-experiment/`）+ 检索/抽题评估（`backend/experiment_reports/` 下 5 份报告）

## 1. 两套实验概况

| 维度 | 聚类实验（题目入库） | 检索实验（题目出库） |
|------|---------------------|---------------------|
| 场景 | 新题导入 → 合并到已有聚类 | 模拟面试 → 从题库抽题/检索 |
| 方案 | 标签摘要记忆 + 验证层 | 混合检索（FTS+向量+RRF）+ LLM rerank |
| 关键数据 | 验证层后准确率 88%，漏合并 ~2%，embedding top-20 召回 100% | 纯 SQL 2.8 → 混合检索+rerank 3.5（修复前 1.7）；RAG 上限 4.2 |
| 成本 | ~0.2M token/轮（裁剪+缓存后） | 每次检索 1 次 embedding + 1 次 LLM rerank（~2K token） |

## 2. 共同结论（两份实验独立验证同一真理）

### 2.1 embedding 只做"召回"，不做"决策"——两处实锤

| 场景 | embedding 单独决策 | LLM 决策 |
|------|-------------------|----------|
| 聚类合并判断 | 中文 cosine 0.6-0.7 无法设阈值（历史结论） | 85-90% 准确（验证层后） |
| 检索精排 | cross-encoder 1.9 分（bge-reranker-v2-m3，训练域不匹配） | LLM rerank 3.5 分 |

**结论**：无论入库还是出库，embedding 负责"把可能相关的捞回来"（召回层），LLM 负责"判定到底相不相关/合不合并"（决策层）。两段式是唯一被两份实验同时验证的结构。

### 2.2 候选裁剪的边界 = embedding 召回质量

- 聚类：字符 jaccard 裁剪 top-20 只召回 86%（漏 6033/6236）；**换 bge-m3 后 top-20 召回 100%**
- 检索：混合检索（FTS 兜底）3.5 > 纯向量 2.9（JVM 场景 FTS 5.0 vs 向量 0.0）

**结论**：裁剪/候选生成必须用 embedding（或混合信号），字符信号不可用；**单一信号有盲区，混合信号互补**（聚类未来可借鉴 FTS/关键词增强候选）。

### 2.3 LLM 判断的不稳定性是共同敌人

- 聚类：同一题三轮判断三种结论；验证层 similarity 分数波动（sim=0.00 配"考察点一致"）→ 最终用"两轮布尔一致"而非分数门槛
- 检索：LLM rerank 分数不稳定（业界 ZeroEntropy 证实 LLM 评分跨次波动）；mimo 评分多次解析失败需容错

**结论**：凡是用 LLM 做决策，都要防"单次判断不可靠"——聚类用验证层（两轮一致），检索用 rerank 排序而非阈值过滤。

### 2.4 mimo 的坑在两处都踩到（已用兼容层解决）

| 坑 | 现象 | 修复 |
|----|------|------|
| json_object 截断 | 输出被掐断（`'```json\n['`） | 能力矩阵降级 prompt 指令 + 容错解析（llm.py 兼容层） |
| thinking 吃 token | 长 prompt 返回空（rerank 全失效） | raw_llm_call 默认 thinking disabled（`c2a1190`） |
| 评分波动 | 打分解析失败率波动 | norm_score_list 碎片恢复 + int 归一 |

### 2.5 成本控制三板斧（两处共用）

1. **候选裁剪**：聚类 top-20 标签（0.96M→0.2M token）；检索 rerank 只对 top-15
2. **缓存持久化**：embedding 向量缓存（题库 320 题一次编码复用）；标签摘要持久化
3. **重试上限**：R6 教训（mimo 抖动时 788 次重试烧 3.56M token）→ tenacity 上限 + 熔断

## 3. 互相借鉴点

| 聚类 → 检索 | 检索 → 聚类 |
|------------|------------|
| 验证层（两轮布尔一致）可借鉴为 rerank 的"双模型投票"（候选数少时可负担） | 混合信号（FTS+向量+RRF）可借鉴为聚类的候选生成（当前仅 embedding+文本预筛） |
| 标签摘要记忆 = 聚类级"语义缓存"，检索未来可复用（候选池带语义标签） | 候选池萎缩教训（question_type 关键词过滤）→ 聚类的 cat2 分组过滤同样有漏匹配风险 |
| 文本预筛（零成本确定性合并） | LLM rerank 的对话上下文优势 → 聚类匹配 prompt 可带上下文（用户岗位/面经来源） |

## 4. 统一架构：题目生命周期视角

```
┌───────────── 入库（聚类）──────────────┐    ┌───────────── 出库（检索/抽题）─────────────┐
│ 新题 → bge-m3 top-20 候选聚类           │    │ query → hybrid(FTS+bge-m3+RRF) top-15     │
│      → LLM 分配（标签摘要列表）          │    │      → LLM rerank（对话上下文）→ top-5     │
│      → 验证层（两轮布尔一致）            │    │      → select_question 绑定              │
│      → 文本预筛前置（零成本）            │    │      （修复后 3.5 分，上限 4.2）           │
└───────────────────────────────────────┘    └───────────────────────────────────────────┘
          共用：bge-m3 embedding（SiliconFlow 缓存）
                LLM 调用层（三格式兼容 + json 降级 + thinking 控制）
                "embedding 召回 + LLM 精判"两段式
```

**关键洞察**：入库聚类和出库检索本质是**同一问题的两个方向**——都是"在 320 题的语义空间中，找到与输入（新题/查询）最相关的题"：
- 聚类：输入=新题，找"相同考察点的题"（合并）
- 检索：输入=查询意图，找"该问的题"（追问）
- 共用的核心资产：**bge-m3 语义索引 + LLM 考察点判断**

## 5. 下一步建议（按收益排序）

1. **检索 rerank 优化**（已验证 3.5 → 4.2 空间）：LLM listwise（从 15 候选选 top-3，替代 pointwise 打分阈值）——抽题评估 C 方案已验证
2. **聚类候选生成加混合信号**：借鉴检索的 FTS/关键词增强（当前仅 embedding+文本预筛，有 2% 漏合并）
3. **聚类验证层 ↔ 检索 rerank 统一**：同一套"LLM 判断 + 容错"工具化（`llm_judge` 模块），避免两处重复实现
4. **embedding 索引统一管理**：聚类向量与检索向量同一份（已实现——DB 全量重算 bge-m3），维护一个 FAISS 索引服务供两端用

## 6. 一句话总结

**两份实验殊途同归：中文面试题的语义系统，"召回靠 embedding、决策靠 LLM、稳定靠多轮一致、省钱靠裁剪缓存"——入库（聚类）与出库（检索）共用同一套两段式架构和同一个 bge-m3 索引，优化的下一步都在"LLM 决策层"（聚类验证层已就绪，检索 rerank 待升级为 listwise）。**
