### 1.3 搜索覆盖率

- 常见关键词覆盖: **155/234 (66.2%)**
- 意味着约 34% 的题目无法被常见关键词检索到

### 1.4 问题诊断

#### 问题 1: Redis 搜索误匹配
```
✗ [5872] 高并发的场景下，怎样做限流？ | tags: 高并发限流
✗ [5894] Agent开发，记忆怎么进行管理？ | tags: 上下文管理, 记忆管理
```
**根因**: FTS5 搜索匹配了 `ai_answer` 字段（包含 Redis 关键词），而非 `question` 字段。

#### 问题 2: Docker 搜索误匹配
```
✗ [6071] 介绍一下OpenClaw和Hermes架构的区别 | tags: Agent架构设计
```
**根因**: `ai_answer` 字段包含 Docker 关键词，但题目本身不相关。

#### 问题 3: TCP 搜索无结果
```
题库中有 [6302] 说一下TCP三次握手和四次挥手的过程
但 FTS5 搜索 "TCP" 返回 0 结果
```
**根因**: FTS5 的 unicode61 tokenizer 对英文缩写的分词可能有问题。

### 1.5 改进建议

1. **搜索范围优化**: 搜索时优先匹配 `question` 和 `tags` 字段，降低 `ai_answer` 字段权重
2. **FTS 索引清理**: 删除冗余的 FTS5 条目
3. **CJK 分词优化**: 考虑使用 jieba 分词替代简单的 2 字窗口滑动
4. **搜索结果排序**: 引入相关性分数，优先返回 question 字段匹配的结果

## 第三部分：综合评估与改进建议

### 3.1 问答检索 RAG

**现状**: ⭐⭐⭐☆☆ (60%)

**优点:**
- FTS5 索引覆盖率高 (141.5%)
- 中文关键词搜索效果好
- 中英混合搜索精准

**问题:**
1. `ai_answer` 字段导致误匹配
2. 英文缩写 (TCP) 搜索失败
3. 搜索覆盖率仅 66.2%

**改进方向:**
1. 搜索时降低 `ai_answer` 字段权重
2. 优化 FTS5 tokenizer 配置
3. 增加 `tags` 字段的搜索权重

### 3.2 聚类 RAG (粗排+精排)

**现状**: ⭐⭐☆☆☆ (40%)

**优点:**
- 130 次合并操作，0 回滚
- 高置信度合并质量好
- 二级分类分布合理

**严重问题:**
1. **embedding 覆盖率 0%** — 粗排完全失效
2. **95.4% 合并置信度 <0.5** — 精排质量存疑
3. **1 对重复题目未合并**

**改进方向:**
1. **紧急**: 为所有题目生成并存储 embedding
2. 检查粗排预筛选逻辑是否正确调用
3. 优化 LLM 精排 prompt，提高置信度校准
4. 添加重复检测的兜底逻辑

### 3.3 优先级排序

| 优先级 | 任务 | 影响 |
|--------|------|------|
| P0 | 为题目生成 embedding | 粗排从 0% → 预期 80%+ |
| P1 | 优化 FTS 搜索权重 | 搜索相关性从 80% → 90%+ |
| P1 | 检查聚类置信度记录 | 排除是记录 bug 还是真实质量差 |
| P2 | 清理冗余 FTS 索引 | 减少存储，提高查询效率 |
| P2 | 添加重复检测兜底 | 避免遗漏重复题目 |
