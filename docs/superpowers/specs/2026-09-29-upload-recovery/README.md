## 1. 目标与不可接受的交付

最终用户能够回答：这份面经属于哪个库、原文是否保存、题目在哪里、处理到哪一步、为何停住、怎么继续。恢复不能丢掉已完成成果，也不能制造重复面经、题目关联或答案任务。

禁止以下“局部修复”作为完成标准：

- 仅新增重试按钮，后台仍从头提取并INSERT。
- 仅把进度改成100%，不检查聚类、答案和审核结果。
- 仅改旧SSE入口，遗漏`/api/submit-jobs`、worker和重试。
- 仅用owner_id筛选UI，通用任务结果接口仍泄露私人内容。
- 仅保存review_json，最终公开内容仍取原始snapshot。
- 仅提高LIMIT或拉全量，面经列表仍前端假分页。
- 以“测试全绿”代替本spec逐项验收；既有测试曾全部通过但遗漏关键反例。

## 3. 二对二权限和费用

| 主体 → 目标 | 写入/审核 | 提交前预检与阶段凭据scope | 可见内容 |
|---|---|---|---|
| 普通用户 → 私人 | 本人直接入库 | 提交前检查user可用；处理用本人user配置 | 本人原文、明细、私人题与公共引用 |
| 普通用户 → 公共 | 提交前检查global公共模型；先私人保存并生成待审快照；批准后公共处理 | 预检global；审核前私人阶段用user；批准后公共阶段用global | 提交者看自己的申请；其他用户只看published投影 |
| 管理员 → 自己私人 | 和普通用户一样 | 提交前检查管理员自己的user配置；处理用该配置 | 自己的私人内容 |
| 管理员 → 公共 | 显式公共导入；视为记录了审批的公共处理 | 提交前检查global；处理从提取开始用global | 未published仅发起者/公共治理人员；published对用户开放 |

所有“actor、owner、payer、reviewer”分开记录。服务端根据认证主体计算，不信任客户端传入is_admin/owner_id/credential_scope。公开题的用户笔记、练习记录、个性化答案仍是私人数据，不随题目共享。

公共目标的预检与阶段费用归属是两个独立判断：普通用户申请公共化时，必须在任何上传分析工作启动前确认global公共模型可用；若其私人暂存阶段还需要个人模型，也必须确认提交者user配置可用。global预检失败时任务保留为needs_action且不开始提取，用户看到“公共模型暂不可用，等待管理员修复”；管理员修复后可从同一任务继续。不得因此改用提交者Key做公共处理。

## 5. 状态与用户旅程

### 5.1 上传业务状态

`queued → running → completed`为正常计算路径；中间允许`waiting_review`、`needs_action`、`partial_failed`、`failed`。已完成或已拒绝审核不自动触发新尝试。

- queued：存在可运行但尚未开始的工作。
- running：至少一个有效租约执行工作。
- waiting_review：私人步骤完成，公共贡献待审核；结果仍能打开。
- needs_action：Key/配置/权限/预算/历史映射歧义阻塞；必须给明确下一步。
- partial_failed：有有效成果且剩余步骤失败。
- failed：没有可用业务成果且计算失败，原稿仍可恢复。
- completed：所有当前要求的步骤均成功或有明确skip理由。审核拒绝/撤回以review_status展示，成功保留私人结果，不假装已发布。

聚合顺序：有实际执行工作→running；无执行但有到期/退避排队工作→queued；无可运行工作且有配置/权限阻塞→needs_action；有技术失败→按是否有成果选partial_failed/failed；只剩审核→waiting_review；否则completed。`warnings`和`review_status`独立存在，不能被聚合状态覆盖。

### 5.2 私人流程

校验→原稿及根任务落库→提取检查点→分类检查点→保存面经与明细→持久化原题匹配决策→个人聚类/公共只读引用→新增题答案→结果入口。

匹配只在一个最终resolution写入点定案。不能上传阶段先丢弃公共命中，异步阶段再独立重新决定。私人匹配成功引用公共题不写公共来源、频次或答案。

### 5.3 公共贡献流程

本人私人原稿和明细→提交不可变快照→审核预览与编辑→原子批准→审核投影的公共处理队列→公共规范题关联提交→逐题published→公共答案。

审批通过不等于published；public_interview/questions_detail在处理完成前不能被普通用户的面经、搜索、统计、来源接口查询出来。公共面经清单只包含已published且未删除的明细。

### 5.4 恢复流程

先GET根任务快照，检查是否已有活跃attempt；有则返回当前attempt。没有则事务内建立新attempt，仅重建未完成/失败/失效步骤。已经成功并版本匹配的提取、分类、入库、resolution、答案必须复用。

恢复接口不是“重新分析”。用户想用新分类体系重算旧成果，应走显式重分析新版本，不偷偷在重试中改变已成功步骤的含义。

## 7. 前端行为要求

- 上传页有标题/文件名、目标库、费用来源说明。HTTP400/413保留输入并展示具体错误；未接受前不显示虚构的后台job。
- 服务端接受后立刻展示根任务卡片。顶部仅做摘要；任务中心保留全部成功、失败、待审核和待配置任务，不能5秒后失去唯一入口。
- 单卡显示：目标、阶段、已完成题数/总数、可用结果、阻塞原因、操作。阶段分母未确定时显示不确定进度，不伪造百分比。
- 只显示服务端allowed_actions。user scope阻塞显示“配置个人模型后继续”；普通用户公共申请遇global阻塞显示“公共模型暂不可用，等待管理员修复”，不显示个人配置入口；修复后可从同一root继续。部分失败为“重试失败步骤”；没有暂停能力时禁止显示暂停。
- 折叠卡片/关闭浮层不删除服务端任务。退出账号时断开SSE并清内存；缓存按user_id隔离。
- 上传完成不打断当前浏览；“查看面经”主动定位。页面仍在第2页时不得仅刷新后声称新结果不存在。
- 修改岗位/招聘季/排序/每页数量后页码回到1；返回任务结果时可切换到该面经所属岗位并明确提示。
- 375px和1440px均可查看任务与恢复按钮；键盘可操作；状态更新使用aria-live=polite，不能每次心跳抢焦点。

## 8. 范围限制与兼容

- 不更换数据库、消息队列或全站模型配置系统；严格scope先限定本上传/发布链路，其他调用方兼容行为不得顺手改变。
- 不引入私有共享链接、团队题库、跨用户协作或自动公开私人源。
- JD使用同一任务/审核外壳，已有JD导入必须回归；JD无题目resolution/聚类阶段，显式skip。不得将面经题目状态强加给JD。
- 新上传双入口统一入持久流程，旧SSE作为创建任务后订阅的兼容适配器。禁止保留两套可写图执行入口。
- 新模型支持旧jobs、旧status字段，禁止把全站jobs状态枚举一次性替换。详见contracts兼容层。
- 本spec不授权执行生产修复、外部推送或部署。实施可提交本地验证单元；生产切换需按项目已有授权范围执行。
