# 洞察工作台设计规格

日期：2026-08-04
状态：已批准，进入 MVP 实现

## 1. 背景

当前“洞察”分组只有“知识图谱”一个入口。图谱由题库的 `cat1`、`cat2` 和 `tags` 构建，节点大小表示题目数量，边表示标签共现；点击节点只会带着筛选条件跳回题库。它适合探索题库，但不能回答面试准备中的核心问题：目标岗位要求什么、个人还缺什么、下一步该练什么。

项目已有可用于洞察的事实：

- JD：岗位、公司、技术栈、招聘季；
- 面经：公司、轮次、岗位、面试题；
- 题库：分类、标签、难度、频次、岗位；
- 模拟面试：会话、消息、面试阶段、追问方向和问题来源；
- 练习：题目练习历史和评分（当前数据库可能为空，必须诚实展示证据不足）。

## 2. 目标

将“洞察”改造成面试准备决策工作台，首期提供三个单独 Tab：

1. **总览**：告诉用户当前最重要的准备任务；
2. **岗位准备度**：比较岗位需求、题库覆盖和个人证据；
3. **面试复盘**：按场次回看面试覆盖和后续训练入口。

知识图谱保留为“岗位准备度”中的辅助探索视图，不再作为一级入口。训练进度/遗忘提醒暂不拆成独立 Tab，待练习事件和评分数据积累后再加入。

## 3. 非目标

- 首期不生成未经证据支持的 0–100 “面试通过率”；
- 首期不引入新的 LLM 调用；
- 首期不改动现有题库、JD、面经和聊天写入流程；
- 首期不删除 `KnowledgeGraph.vue`，保持旧图谱功能可访问；
- 首期不实现复杂的间隔重复算法。

## 4. 信息架构与路由

侧栏“洞察”分组调整为：

| Tab | 路由 | 核心问题 |
|---|---|---|
| 总览 | `/insights/overview` | 我现在最该做什么？ |
| 岗位准备度 | `/insights/readiness` | 这个岗位要求什么，我覆盖得怎么样？ |
| 面试复盘 | `/insights/reviews` | 我刚才面试哪里没答好？ |

旧路由 `/knowledge-graph` 重定向到 `/insights/readiness?view=graph`，保证已有书签和入口可用。

## 5. 后端 API 契约

新增认证接口：`GET /api/insights`

返回一个聚合快照，按当前用户和当前岗位隔离：

```json
{
  "version": 1,
  "target_position": {
    "name": "agent开发/大模型应用开发/大模型开发",
    "source": "user_position"
  },
  "summary": {
    "question_count": 268,
    "jd_count": 9,
    "interview_count": 46,
    "practiced_question_count": 0,
    "evaluated_answer_count": 0,
    "evidence_state": "insufficient"
  },
  "actions": [
    {
      "id": "topic:B2.RAG系统设计",
      "title": "RAG系统设计",
      "description": "题库覆盖充分，但还没有个人练习证据。",
      "question_count": 25,
      "priority": "high",
      "action": "开始练习"
    }
  ],
  "readiness": {
    "items": [
      {
        "id": "B2.RAG系统设计",
        "name": "RAG系统设计",
        "question_count": 25,
        "question_frequency": 35,
        "practice_count": 0,
        "average_score": null,
        "status": "not_started",
        "reason": "尚无个人练习记录"
      }
    ]
  },
  "reviews": {
    "total": 0,
    "items": []
  },
  "data_quality": {
    "unassigned_question_count": 53,
    "has_practice_evidence": false,
    "message": "当前没有结构化练习评分，准备度仅基于岗位和题库事实。"
  }

```

### 数据口径

- 题库沿用 `build_bank_where_clause(user_id, "all")`，并过滤软删除数据；
- JD/面经只统计公共已审核数据和当前用户私有数据，并按当前岗位过滤；
- 个人练习只统计 `user_practice_history.user_id = 当前用户`；
- 复盘只统计 `chat_conversations.user_id = 当前用户`，不读取其他用户或测试会话；
- `question_frequency` 用题库频次聚合，不能解释为个人掌握度；
- 没有练习证据时，状态必须是 `not_started` / `insufficient`，不能伪造分数。

## 6. 页面设计

### 6.1 总览

- 顶部展示目标岗位和数据证据状态；
- 统计卡片：岗位 JD 数、面经数、题库题数、已练题数；
- “本周最该做”卡片：最多 3 个高优先级主题；
- 每个行动卡片提供跳转到岗位准备度或题目抽测的入口；
- 没有评分时展示“尚未形成个人能力分数”，而不是 0 分。

### 6.2 岗位准备度

- 展示按 `cat2` 聚合的能力矩阵；
- 字段包括岗位热度/题库数量/个人练习次数/平均分/状态/理由；
- 默认使用表格或列表，优先于图谱；
- 提供“打开知识图谱”按钮，加载现有图谱作为探索视图；
- 旧图谱页面的点击筛选行为保持兼容。

### 6.3 面试复盘

- 有会话时显示最近会话、消息数、最近更新时间、岗位和模式；
- 没有可用会话时展示空状态和“开始一次模拟面试”入口；
- 不把没有结构化评分的聊天消息推断为弱项；
- 后续可在同一接口中加入阶段覆盖、追问次数和答案评价。

## 7. 状态定义

| 状态 | 条件 |
|---|---|
| `not_started` | 该主题没有个人练习记录 |
| `needs_work` | 有练习记录且平均分低于 60 |
| `developing` | 有练习记录且平均分为 60–79 |
| `stable` | 有练习记录且平均分不低于 80 |

如果没有评分但存在其他个人证据，展示 `evidence_only`，不计算平均分。

## 8. 验收标准

- 侧栏“洞察”有 3 个可访问 Tab，桌面和移动导航顺序一致；
- `/insights/overview` 默认渲染总览，`/insights/readiness` 渲染岗位准备度，`/insights/reviews` 渲染面试复盘；
- `/knowledge-graph` 重定向后仍能打开图谱；
- API 按用户/岗位隔离，软删除题目不计入统计；
- 没有个人练习评分时，页面不显示虚假的能力分数；
- 后端单测覆盖统计口径、状态计算和用户隔离；
- 前端 Playwright 测试 mock `/api/insights`，覆盖三个 Tab 的导航和关键文案；
- `npm run build` 通过，后端定向测试通过。

## 9. 参考启发

- LeetCode：目标计划、周任务、任务日历、动态题单和提交分析；
- 牛客：按岗位拆分学习路径、题型和公司真题，并记录学习进度；
- Yoodli：结构化评价维度、每次练习后的具体改进建议和下一步训练；
- Seconda：简历驱动的定制面试、多维评分和深度复盘。

这些产品的共同点是把数据连接到下一步行动，而不是把可视化本身当成洞察。
