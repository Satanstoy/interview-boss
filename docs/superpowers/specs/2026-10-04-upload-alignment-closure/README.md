## 1. 依据与优先级

本规格是 2026-09-29 上传恢复 Draft 的闭环补充，不取代原文，不重开已通过的 AC。来源和当前对账见：[原上传恢复规格](../2026-09-29-upload-recovery/README.md)、[验收矩阵](../2026-09-29-upload-recovery/acceptance.md)、[接口和数据契约](../2026-09-29-upload-recovery/contracts.md)、[2026-10-02 全量对账](../../../verification/upload-recovery/2026-10-02-spec-audit.md)。公共/个人数据边界以[已接受 ADR-0048](../../../adr/0048-public-personal-question-bank-boundaries.md)为准。

冲突处理顺序：

1. ADR-0048 的已接受权限、归属和发布规则优先。
2. 2026-09-29 上传恢复规格中已明确且不与 ADR 冲突的行为保持有效。
3. 本补充对 AC-001、002、007、009、010、011、013、016、017、022、024 增加更具体的边界与验收。重叠时以本补充为准。
4. 旧代码、旧测试和审计探针都不是行为规范。测试期望与上述规则冲突时，必须修正测试期望，不得据此放宽规范。

本次对账记录为 18 项通过、11 项部分。11 项“部分”表示缺少至少一项规范要求的证据，不自动表示生产行为已被证实错误。当前未闭环事实按项列于[验收表](acceptance.md)，已通过项保留为不可回归边界。

## 2. 目标与范围

目标是让 11 项部分对齐项都达到：行为定义无歧义、反例有测试、测试使用真实 API/数据库/队列/worker/UI 的范围明确、运行结果可追溯。每一项通过后，必须有对应的命令结果和 AC 证据；只看代码、只跑 mock UI、只见 HTTP 200 或只见任务显示 completed 均不算通过。

范围仅包括：

- AC-001：审核发布后的公共结果可从原任务卡片定位。
- AC-002：面经分页由 UI 到真实服务端分页 API 闭环。
- AC-007：队列公平续调以及所有者重试本人可恢复的终态失败任务。
- AC-009：两个用户、多个 worker 的并发输入隔离。
- AC-010：真实 SSE/快照故障下的浏览器恢复与账号切换隔离。
- AC-011：多题答案部分失败、任务聚合和只重试失败题。
- AC-013：鉴权、限流、结构错误的真实 HTTP stub、统一重试预算和旧 SSE 兼容。
- AC-016：同一公共面经追加贡献的累计投影与失败恢复。
- AC-017：跨 attempt 恢复、同一活跃 attempt 幂等及并发提交。
- AC-022：真实上传错误后的草稿保留及修正重提。
- AC-024：JD 旧重试、审核发布与旧数据兼容。

已通过 AC-003～006、008、012、014、015、018～021、023、025～029 不在本次重开范围。它们只作为回归边界；若新改动触及其路径，定向回归必须继续通过。

明确不在范围：重做 ADR-0048、改写无关 spec、修复仓库全部 E2E/mock debt、验证过期的真实模型凭据或生成质量、向生产数据库写验收数据、生产发布审批。外部模型调用须在有效凭据、费用授权和单独验收决定后另行进行。

## 4. 已确认决策

### 3.1 AC-007：所有者可重试自己的可恢复任务

项目所有者已确认：普通用户可以从任务中心重试自己拥有且仍有可恢复工作的终态失败任务。upload root 使用原 root/attempt/checkpoint 业务身份，只恢复失败、缺失或失效步骤并复用有效成功检查点。私人 rootless 失败项使用原 `analysis_queue.id`，只把该行重新排队，不制造 upload root、attempt 或 checkpoint；周期对账从 durable pending 行修复状态提交后的调度空窗。上传 root 的成功成果不得重做；rootless 的验收则核对 queue ID、owner scope、root-null、处理状态和私人题库投影。任务重试不得重置 upload root 的用户日配额、系统日预算或每导入任务预算。

用户不能借管理员身份重试其他用户的私有任务。管理员对已审核公共贡献失败子项的处理继续使用现有专用管理员入口；普通用户入口不得改变审核状态或绕过发布门槛。任务身份无法安全解析、来源已删除、版本不兼容、预算耗尽或权限不足时，服务端不得猜测、复制任务或派发新工作，必须返回可解释的阻塞状态。

同一 upload root 已有活跃 attempt 时，重复或并发点击都返回该活跃 attempt（`created_attempt=false`），不得创建第二个。rootless 队列项的重复或并发点击收敛到同一 `queue_id`，最多一次从 `failed` 改为 `pending`，不新增队列行。用户修复自己的模型配置后可以显式再次恢复；系统模型阻塞须等管理员修复，不得回退到用户 Key。

### 3.2 验收模型与模型 stub

闭环验收使用本地确定性 HTTP 模型 stub。stub 只替代模型供应商边界；浏览器、鉴权、后端 API、SQLite、Redis、ARQ dispatcher、worker 和公开读取都运行真实候选镜像。不得把整个业务 API 或 worker mock 成成功响应。AC-013 的 401、429、超时和结构错误由 stub 可控返回。

验收数据必须写入临时 SQLite volume 和随机 Redis namespace。候选镜像的浏览器验收不得读写生产数据库。生产环境可以做只读健康检查，但不能用生产探针替代下面的行为验收。

## 5. 全局完成门槛

只有同时满足以下条件，才能将本补充及 11 个 AC 标记为“通过”：

1. 上表 11 个 `CL-REQ-*` 均映射到同号 `CL-AC-*` 和可执行验证；没有 TBD、未定行为或无归属的验收项。
2. 每个 AC 的规定反例、并发条件、身份、数量、排序、状态及数据库关系均有断言；不以截图或状态码代替数据检查。
3. 受影响的单元/服务回归通过，并且候选镜像在隔离部署栈中通过所有 11 个 AC 的浏览器/API 场景。测试结果记录具体镜像 digest、命令、退出码、passed/failed/skipped 数量和场景到 AC 的映射。
4. 生产只做镜像一致性、服务健康和 HTTP health 探针；业务验收数据留在 disposable 栈。stub 的结果不能被描述成真实供应商/真实模型质量验收。
5. `failed`、`partial_failed`、`needs_action`、`waiting_review` 等状态按契约显示；任何场景都不得误报 completed、重复成果、泄漏跨用户内容或提前公开未审核/未处理数据。
6. 无通过项被删除、skip、降级为 mock、改成宽松断言或通过增加重试额度来掩盖。若环境故障导致未运行，状态保持“未运行”，不算通过。
