# 评测体系与 Harness 效果审计

日期：2026-08-20
范围：本地 `backend/data/interview-boss.db`、评测 Adapter/Scorer、`evals/suites`、管理员评测 API 与前端版本展示。

## 结论

现有低分不是单一原因：

- 模拟面试的低分首先有明显的评测契约问题，旧版 1.0 把产品真实的开场 `chat` 判成了必须为 `interview_question`，并要求 `search_questions`，而生产链路实际使用 `draw_questions`。这部分不能归因于 Harness。
- 题目分类的低分主要是真实 Harness/模型输出问题：多条结果的一级分类、二级分类或输出结构为空/错位，且在不同运行中重复出现。评测集的严格标签检查揭示了问题，但不是问题的主要来源。
- 面经提取、JD 提取和简历分析的全绿结果证据不足，不能直接证明 Harness 很好：样本少、只执行了单次 replication，且结构化检查偏宽，缺少人工复核和更强的语义覆盖检查。

因此当前应把“评测集契约错误”“Harness 真实失败”“样本/评分能力不足”分开呈现，不能只看最终平均分。

## 数据概况

数据库中共有 21 条评测 Run、68 个 Attempt、39 个 Benchmark Case。有效完成结果主要集中在 Run 5–21；没有可供复核的持久化 Artifact，也没有人工 Review 记录作为独立校准来源。Manifest 标称的 replication 次数与历史存量 Run 的实际执行次数不一致，历史结果应按低置信度处理。

| 目标 | 已完成样本 | 现象 | 判断 |
| --- | ---: | --- | --- |
| 面经提取 | 9 | 9/9 通过，分数均为 1.0 | 通过，但题集和 scorer 偏弱，证据不足 |
| JD 提取 | 7 | 7/7 通过，分数均为 1.0 | 通过，但题集和 scorer 偏弱，证据不足 |
| 简历分析 | 6 | 约 0.95–1.0，硬门槛通过 | 有限通过；另有 2 个 worker timeout |
| 题目分类 | 9 | 9/9 硬门槛失败，分数约 0–0.75 | 主要是 Harness/模型输出不稳定 |
| 模拟面试 | 9 个已完成 Case，另有失败/取消 | 已完成项全部受旧契约或行为断言影响 | 评测契约与 Harness 问题混合 |

## 分目标分析

### 模拟面试

Run 9、12、17 中，生产对话链路大多能够产生回复和工具事件，但旧 1.0 Case 的第一轮意图要求与真实开场不一致；`tool_timing` 的工具名称也与实际链路不一致。旧 Adapter 还没有消费 Case 的 `harness_context.tool_fixture`，因此“声明有 deterministic fixture”并不等于真实运行使用了该 fixture。

剩余问题中，错误纠正场景的 Faiss 纠正证据不足、部分工具结果没有稳定转化为后续问题，这些才是更接近真实 Harness 能力的问题。

另外，旧 Adapter 对未实现的断言 ID 曾经用“有任意一轮对话就算通过”的兜底逻辑。这会制造假绿；现在已改为显式失败并记录 `unsupported interview assertion`，后续需要继续把这些断言实现为有证据的检查。

### 题目分类

Run 8 的 4 条结果分数为 0、0、0.5、0.75；Run 21 为 0.08、0.08、0、0.65。典型结果是标签列出现空值、分类列错位，或者只给出了主题标签而没有符合 taxonomy 的一级/二级分类。难度标签有时是正确的，说明并非所有输出都失败，但结构化协议和分类决策不稳定。

这里评测集的精确标签要求是合理的，因为管理员确实需要知道题目被分到了哪里；需要补充的是“输出格式错误”和“分类决策错误”两个独立指标，不能只合并成一个硬失败。

### 面经提取、JD 提取和简历分析

这些目标的结果几乎全绿，但存量 Case 数量很小，且主要依赖字段是否存在、字符串是否匹配、建议条数和禁止虚构声明等结构性条件。它们没有充分覆盖同义表达、冲突信息、漏提、过度推断和边界格式。因此结论应写成“当前样本下结构检查通过”，而不是“Harness 整体质量已验证”。

## 已做的评测集调整

新增 `interview-e2e` 1.1，版本只提升 0.1，保留 Case 集合和历史 1.0：

- 第一轮意图按生产开场改为 `chat`；
- `tool_timing` 改为真实链路使用的 `draw_questions`；
- 错误纠正场景的第一轮策略改为 `clarification`；
- 保留旧版 1.0，保证历史结果仍可追溯。

这次变更修复的是“评测契约和生产行为不一致”，不是为了让 Harness 得分变好而放宽标准。

## 版本与结果边界

现在每个目标类型都有项目级 Harness Registry。普通 Run 使用项目变量 `PROJECT_HARNESS_VERSION`，A/B Run 可以显式选择两个已发布 Harness 版本；每条 Run 都冻结 Harness 的版本、Git SHA、镜像摘要、配置摘要和 Manifest 摘要。A/B 只允许 Harness 不同，评测集、协议、Case、随机种子和环境必须一致。

历史 Dual-axis Run 中无法可靠推断项目 Harness 的，保持空值并在前端显示“历史数据未记录”，不把 Eval Manifest 中的内部模拟器字段冒充为项目 Harness 版本。

## 后续优先级

1. 为 1.1 中尚未实现的面试行为断言补上真实证据检查，并将“评测断言未实现”与 Harness 失败分开统计。
2. 给题目分类拆分“格式有效性、taxonomy 正确性、难度正确性”，避免一个硬门槛掩盖具体失败位置。
3. 为提取和简历评测增加语义变体、冲突信息和人工校准样本，并真正执行 replication。
4. 让运行环境在启动时把项目 Harness 的 Git SHA、镜像摘要和配置摘要写入 Registry，避免 `current-code-state` / `local-baseline` 长期作为生产身份。
